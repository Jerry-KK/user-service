# 签到模块架构演进与包结构说明

## 架构核心思想
本项目参考 **六边形架构（Ports and Adapters）** 进行解耦重构：
1. **依赖向内与控制反转**：核心业务层（`Service`/`Domain`）仅处理业务逻辑，不依赖任何持久化（MyBatis）或中间件（RabbitMQ）细节。
2. **模型职责隔离**：拒绝 `PO/Entity` 一贯到底。划分 `Domain`（业务实体）、`PO`（数据库表映射）、`Event`（事件消息）、`DTO/VO`（传输展示对象），并在适配器边缘完成数据转换。
3. **接口与适配分离**：核心层通过出站接口调用外部能力，数据库与 MQ 均作为适配器（`Adapter`）插拔实现，大幅提升可测试性与扩展性。

---

## 包结构映射说明 (`cn.lethekk.userservice`)

```text
cn.lethekk.userservice
├── adapter                // 适配器层（收拢外部协议与数据转换）
│   ├── inbound            // 入站适配器（MQ消费者、定时任务等）
│   └── outbound           // 出站适配器（Repository实现、EventPublisher消息适配器）
├── model                  // 数据模型定义
│   ├── domain             // 核心业务领域对象（贯穿 Service 层）
│   ├── po                 // 数据库持久化对象（Mapper 对应实体）
│   ├── event              // 业务事件传输对象
│   └── dto / vo           // 接口输入输出对象
├── service                // 核心业务编排（仅依赖 Domain 与 出站接口）
├── controller             // HTTP 接口入口（后续可归入 adapter.inbound.rest）
├── dao                    // 数据访问接口（MyBatis Mapper）
├── mq                     // MQ 基础设施与事务发件箱（Outbox）落地
└── config / utils         // 配置与通用工具
```
## 重构收益总结
- 单测解耦：测试 Service 时仅需 Mock Repository 接口，脱离数据库和 MQ 环境运行。
- 边界清晰：消除面向过程编程，数据转换（如 Domain -> PO）统一收拢在 Adapter 层。
- 渐进演进：保持工程实用性，避免过度设计，后期可平滑将 dao/mq 收拢至 infrastructure 基础设施包。
